## 1. NormalUser Model

**Location:** `backend/models/NormalUser.js`

### Purpose
Normal users are the basic consumers of the platform. They can:
- Browse and read news
- Vote on news credibility
- Participate in debate rooms
- Cannot upload news or add comments

### Complete Schema with Explanations

```javascript
const mongoose = require('mongoose');

const normalUserSchema = new mongoose.Schema({
  
  // ═══════════════════════════════════════════════════════════════
  // IDENTITY FIELDS
  // ═══════════════════════════════════════════════════════════════
  
  name: {
    type: String,
    required: true,
  },
  // WHY: Display name for the user
  // WHAT: Full name like "John Doe"
  // HOW: Shown in comments, debate rooms, profiles
  // VALIDATION: Must be provided during signup
  
  username: {
    type: String,
    required: true,
    unique: true,  // Creates database index, enforces uniqueness
  },
  // WHY: Unique identifier for login and mentions
  // WHAT: Like "@johndoe" on Twitter
  // HOW: Used for login, URL slugs (/profile/johndoe)
  // VALIDATION: Must be unique across ALL NormalUser documents
  
  email: {
    type: String,
    required: true,
    unique: true,
  },
  // WHY: Contact and password recovery
  // WHAT: Valid email address
  // HOW: Used for login, notifications, password reset
  // VALIDATION: Must be unique, prevents multiple accounts
  
  
  // ═══════════════════════════════════════════════════════════════
  // AUTHENTICATION FIELDS
  // ═══════════════════════════════════════════════════════════════
  
  password: {
    type: String,
    required: true,
  },
  // WHY: Secure account access
  // WHAT: NEVER stores plain text! Always hashed with bcrypt
  // HOW: Hashed before saving, compared during login
  // EXAMPLE VALUE: "$2b$12$LQv3c1yqBWVHxkd0LHAkCOYz6TtxMQJqhN8/X4e..."
  // SECURITY: 12 salt rounds, irreversible hash
  
  
  // ═══════════════════════════════════════════════════════════════
  // FACE AUTHENTICATION FIELDS
  // ═══════════════════════════════════════════════════════════════
  
  faceEmbedding: {
    type: [Number],  // Array of 512 floating-point numbers
    default: null,
  },
  // WHY: Enable login using face recognition
  // WHAT: 512-dimensional vector representing facial features
  // HOW: Generated by InsightFace/ArcFace AI model
  // EXAMPLE: [0.234, -0.892, 0.445, 0.123, ..., -0.567] (512 numbers)
  // SIZE: 512 x 8 bytes = ~4KB per user
  // USAGE: Compared with live face scan during login
  
  faceRegisteredAt: {
    type: Date,
    default: null,
  },
  // WHY: Track when face auth was set up
  // WHAT: Timestamp of face registration
  // HOW: Set when user successfully registers their face
  
  hasFaceAuth: {
    type: Boolean,
    default: false,
  },
  // WHY: Quick check if user has face auth enabled
  // WHAT: true = face registered, false = not registered
  // HOW: Used in UI to show/hide face login option
  // OPTIMIZATION: Faster than checking if faceEmbedding is null
  
  
  // ═══════════════════════════════════════════════════════════════
  // PROFILE FIELDS
  // ═══════════════════════════════════════════════════════════════
  
  role: {
    type: String,
    default: 'User',  // Could be 'Normal' for consistency
  },
  // WHY: Identify user type in code
  // WHAT: Always 'User' for NormalUser
  // HOW: Used in middleware to check permissions
  
  bio: {
    type: String,
    default: null,
  },
  // WHY: Let users describe themselves
  // WHAT: Short description (e.g., "Tech enthusiast from NYC")
  // HOW: Displayed on profile page
  
  interests: {
    type: [String],
    default: null,
  },
  // WHY: Personalization and recommendations
  // WHAT: Array of topics like ["technology", "politics", "health"]
  // HOW: Could be used for news feed personalization
  
  
  // ═══════════════════════════════════════════════════════════════
  // METADATA FIELDS
  // ═══════════════════════════════════════════════════════════════
  
  createdAt: {
    type: Date,
    default: Date.now,  // Automatically set to current time
  },
  // WHY: Track when account was created
  // WHAT: Timestamp of signup
  // HOW: Used in admin dashboards, analytics
  
});

module.exports = mongoose.model('NormalUser', normalUserSchema);
// Creates collection named 'normalusers' (lowercase + plural)
```

## 2. CommunityUser Model

**Location:** `backend/models/CommunityUser.js`

### Purpose
Community users are verified contributors who can:
- Upload news articles
- Add comments with evidence
- Vote on credibility
- Participate in all platform features

### What Makes CommunityUser Different from NormalUser?

```
NormalUser                          CommunityUser
──────────────────────────────────────────────────────────
Basic fields                        Same basic fields
No approval needed                  ✅ Requires admin approval
No photo                            ✅ Has photo
No location                         ✅ Has location
No social links                     ✅ Has social links
No verification ID                  ✅ Has verification ID
Cannot upload news                  ✅ Can upload news
Cannot comment                      ✅ Can comment
```

### Complete Schema with Explanations

```javascript
const mongoose = require('mongoose');

const communityUserSchema = new mongoose.Schema({
  
  // ═══════════════════════════════════════════════════════════════
  // INHERITED FROM NormalUser (same fields, same purpose)
  // ═══════════════════════════════════════════════════════════════
  
  name: { type: String, required: true },
  username: { type: String, required: true, unique: true },
  email: { type: String, required: true, unique: true },
  password: { type: String, required: true },
  bio: { type: String, default: null },
  interests: { type: [String], default: null },
  role: { type: String, default: 'Community' },
  
  // Face authentication (same as NormalUser)
  faceEmbedding: { type: [Number], default: null },
  faceRegisteredAt: { type: Date, default: null },
  hasFaceAuth: { type: Boolean, default: false },
  
  
  // ═══════════════════════════════════════════════════════════════
  // COMMUNITY USER SPECIFIC FIELDS
  // ═══════════════════════════════════════════════════════════════
  
  verificationId: {
    type: String,
    default: null,
  },
  // WHY: Verify user's identity
  // WHAT: Could be government ID number, press card number, etc.
  // HOW: Admin reviews this during approval process
  // SECURITY: Should be encrypted in production
  
  photo: {
    type: String,
    default: null,
  },
  // WHY: Visual identity verification + profile display
  // WHAT: URL or filename of profile photo
  // HOW: Uploaded during registration, stored in /uploads folder
  // EXAMPLE: "uploads/profiles/user123_photo.jpg"
  
  location: {
    type: String,
    default: null,
  },
  // WHY: Geographic context for local news credibility
  // WHAT: City, state, or country
  // HOW: Self-reported, displayed on profile
  // EXAMPLE: "New York, USA"
  
  socialLinks: {
    twitter: { type: String, default: null },
    linkedin: { type: String, default: null },
    website: { type: String, default: null }
  },
  // WHY: Verify identity through social presence
  // WHAT: URLs to social profiles
  // HOW: Admin can check these during approval
  // EXAMPLE:
  // {
  //   twitter: "https://twitter.com/johndoe",
  //   linkedin: "https://linkedin.com/in/johndoe",
  //   website: "https://johndoe.com"
  // }
  
  
  // ═══════════════════════════════════════════════════════════════
  // APPROVAL WORKFLOW FIELDS
  // ═══════════════════════════════════════════════════════════════
  
  isApproved: {
    type: Boolean,
    default: false,  // IMPORTANT: Starts as false!
  },
  // WHY: Control who can contribute content
  // WHAT: false = pending approval, true = can use full features
  // HOW: Set to true by admin after reviewing application
  // FLOW:
  //   1. User signs up → isApproved = false
  //   2. User waits for admin review
  //   3. Admin approves → isApproved = true
  //   4. User can now upload news, comment, etc.
  
  joinedAt: {
    type: Date,
    default: Date.now,
  },
  // WHY: Track when user became a community member
  // WHAT: Timestamp of approval (or signup)
  // HOW: Could differ from createdAt if there's a delay
  
  createdAt: {
    type: Date,
    default: Date.now,
  },
  
});

module.exports = mongoose.model('CommunityUser', communityUserSchema);
```

## 3. ExpertUser Model

**Location:** `backend/models/ExpertUser.js`

### Purpose
Expert users are verified professionals (journalists, researchers, doctors, etc.) who can:
- Everything Community Users can do
- Provide expert verdicts on news
- Higher credibility weight in AI analysis

### What Makes ExpertUser Different?

```
CommunityUser                       ExpertUser
──────────────────────────────────────────────────────────
All community fields                Same community fields
No expertise area                   ✅ Has areaOfExpertise
No credentials                      ✅ Has credentials array
No experience tracking              ✅ Has experience (years)
No profession field                 ✅ Has profession (required!)
Can comment                         ✅ Can give EXPERT verdicts
```

## How Users Are Used in Code

### 1. Authentication Middleware

```javascript
// middlewares/authMiddleware.js

const authenticateCommunityOrExpertUser = async (req, res, next) => {
  const token = req.cookies.token || req.headers.authorization?.split(' ')[1];
  
  const decoded = jwt.verify(token, process.env.JWT_SECRET);
  
  // Try to find user in either collection
  let user = await CommunityUser.findById(decoded.userId);
  if (!user) {
    user = await ExpertUser.findById(decoded.userId);
  }
  
  if (!user) {
    return res.status(404).json({ message: 'User not found' });
  }
  
  // Check if approved (both types have isApproved)
  if (!user.isApproved) {
    return res.status(403).json({ message: 'Account pending approval' });
  }
  
  req.user = user;
  next();
};
```

## Interview Questions & Answers

### Q1: Why have separate models instead of one User model with a role field?
**Answer:**
1. **Different schemas**: ExpertUser has profession/credentials, NormalUser doesn't
2. **Type safety**: Mongoose validation differs per user type
3. **Query performance**: Querying experts only searches smaller collection
4. **Separation of concerns**: Different business logic per user type
5. **Database indexes**: Optimized per collection

Alternative: Single User model with discriminators (Mongoose inheritance).

### Q2: Why is isApproved default false for CommunityUser?
**Answer:** Security measure to prevent spam/fake accounts:
- Anyone can sign up as CommunityUser
- But they can't upload news until admin reviews them
- Protects platform from malicious content
- Trade-off: Friction in onboarding

### Q3: How does face authentication work across user types?
**Answer:**
- All three user types (Normal, Community, Expert) have face auth fields
- Same 512-number embedding format for all
- Same registration/login process
- Admin doesn't have face auth (different security model)

### Q4: What happens if username is not unique?
**Answer:** MongoDB throws `E11000 duplicate key error`. The application should:
1. Catch this error
2. Return user-friendly message: "Username already taken"
3. Suggest alternative usernames

### Q5: Why store faceEmbedding in user document instead of separate collection?
**Answer:**
- **Pros of embedding**: Single query for login, atomic updates
- **Cons of embedding**: Document size increases (~4KB per user)
- **Decision**: Embedding is fine because it's one-to-one relationship and frequently accessed together

## Summary

- **NormalUser**: Basic consumers, can vote and debate, no content creation
- **CommunityUser**: Verified contributors, can upload news and comment
- **ExpertUser**: Professionals with credentials, highest credibility
- **Admin**: Platform managers, approval power, no content role
- All users except Admin can use face authentication
- CommunityUser and ExpertUser require admin approval
